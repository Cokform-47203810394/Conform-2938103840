# Cokform 실사용 전수 테스트 기록 · 2026-08-18

## 테스트 환경

- 운영 URL: https://cokform.pages.dev
- 제작자 계정: 사용자 제공 Google 로그인 세션
- 테스트 폼: 빈 양식으로 새 폼 1개 생성. 모든 테스트 데이터는 비민감한 감사용 값만 사용하고, 종료 후 삭제 대상이다.

## 제작자 진입 흐름

1. Google 로그인은 정상 완료됐고, 홈의 제작자 상태·템플릿·운영 현황이 표시됐다.
2. `빈 양식`을 누르면 새 편집기와 개인키 금고 모달이 열렸다.
3. 12자 이상 복구 비밀번호를 두 번 입력한 뒤 개인키 금고 생성은 정상적으로 완료됐다.
4. 금고 설정 중에는 편집기 본문이 `불러오는 중…`으로 막힌다. E2EE 안전성에는 타당하지만, 처음 온 제작자에게는 왜 먼저 복구 비밀번호를 정해야 하는지와 백업을 언제 내려받아야 하는지 안내가 더 짧고 강하게 필요하다.
5. 편집기 진입 직후 첫 제목 입력 시 브라우저 입력 도구에서 일시적 연결 오류가 한 번 발생했다. 화면을 다시 확인하자 동일 입력 제어는 유지돼 있었으며, 제품 오류인지 테스트 브라우저 전송 오류인지는 이후 재현으로 판정한다.

## 다음 검증

폼 제목·설명·질문 유형·필수값·운영 설정·공유를 설정한 뒤 별도 공개 응답자 흐름에서 실제 제출을 진행한다.
6. 제목 입력은 첫 시도에서 브라우저 입력 전송 오류가 있었고, 좌표 기반 입력도 실제 값 반영이 확인되지 않았다. 이후 같은 제목 필드를 요소 기준으로 다시 입력하자 정상 반영되고 `저장 중…` 상태가 표시됐다. 이 테스트 도구의 일시적 입력 전송 문제일 가능성이 높지만, 제작자 UI는 제목 입력 후 저장 완료 상태가 짧게 표시돼 실제 저장 완료를 확인하기 어렵다.
7. 첫 문항 제목 영역을 좌표 방식으로 입력하려 했으나 값이 반영되지 않았다. 화면 자동화가 문항 제목을 표준 input·textarea·contenteditable 제어로 식별하지 못했고, DOM 탐색에서도 질문 플레이스홀더를 찾지 못했다. 실제 사람이 클릭해 입력 가능한지 소스 구조와 미리보기로 추가 재현이 필요하다. 이대로라면 자동화 접근성뿐 아니라 키보드·보조기기 호환성 위험 신호다.
8. 소스 확인 결과 문항 제목은 `contentEditable` 기반 리치 텍스트 편집기다. 포커스 없이 자동화 입력하면 실패했지만, 실제 편집 영역을 클릭한 뒤 입력하자 정상 반영됐다. 서식 도구가 포커스 시에만 떠서 제목 입력과 서식 기능 자체는 동작한다.
9. 첫 문항을 `단답형`으로 전환하고 `필수 입력` 토글을 켰다. 문항 제목은 보존됐고 유형 전환·토글 반영·자동저장은 정상으로 확인됐다. 다만 콘텐츠 편집형 제목이 일반 입력 필드처럼 명확한 테두리·레이블을 주지 않아 처음 쓰는 제작자는 클릭 가능 영역을 놓칠 수 있다.
10. 우측 빠른 추가의 `객관식 질문 추가`는 즉시 Q02를 생성했다. 리치 텍스트 제목에 실제 질문을 입력하고 첫 옵션을 `행사 신청`으로 바꾸는 흐름도 성공했다.
11. 문항 제목 편집은 포커스 뒤에만 입력되는 `contentEditable`이라 일반 텍스트 필드보다 조작 진입점이 약하다. 제작자 UI 자체 기능은 동작했지만, 접근성·자동화 친화성은 낮은 편으로 P1 개선 후보로 기록한다.
12. `개인정보 동의 질문 추가`는 수집 목적·수집 항목·보유 기간·거부권 안내·동의/미동의 선택지·미동의 제출 차단 토글을 한 번에 생성했다. 미동의 제출 차단 토글도 켜졌다. 기본 문구는 바로 쓸 수 있는 수준이나, 실제 운영자가 자기 조직·목적·기간에 맞춰 모든 항목을 수정해야 한다는 경고가 카드 내부에 더 분명히 보여야 한다.
13. 객관식 두 번째 옵션 추가·수정도 정상 동작했다.

## P1 · 잠긴 개인키 금고가 폼 편집 전체를 막음 — 수정 진행

폼을 다시 열어 개인키 금고가 잠긴 경우, 기존 구현은 폼 구조까지 불러오지 않고 금고 모달을 닫을 수도 없었다. 응답 평문과 암호화 버전은 금고 잠금 상태에서 보호해야 하지만, 제목·질문·설정처럼 응답 원문이 아닌 폼 구조까지 편집 불가로 만드는 것은 제작자 자유도와 운영 연속성을 크게 떨어뜨린다.

수정안은 잠긴 상태에서도 폼 구조만 로드하고 응답·복호화된 버전은 빈 상태로 유지하는 것이다. 답변 탭과 버전 기록을 열 때만 금고 해제를 요구하고, 응답 암호화 키가 없는 새 폼은 공개 공유·링크 복사를 막는다. 잠긴 금고 모달도 사용자가 닫을 수 있어야 한다. 이 변경은 로컬 빌드를 통과했으며, 배포 뒤 재검증한다.

## 배포 후 재검증

16. 커밋 `80d5648` 배포 뒤 잠긴 개인키 금고 상태로 같은 폼을 다시 열었다. 제목·질문·운영 설정은 즉시 로드되고 편집 가능했다. 답변 탭을 선택하면 금고 열기 안내가 표시됐으며, 모달을 닫아도 다시 편집 화면으로 돌아올 수 있었다. 응답 평문·복호화 버전은 잠금 상태에서 표시되지 않았다. **P1 수정 배포 검증 완료**.
17. 수동 마감 버튼을 눌렀을 때 운영 카드 상태, 홈의 폼 배지, 공개 응답 화면이 모두 `마감`으로 일치했다. 공개 화면에는 입력 컨트롤 대신 `작성자가 현재 응답을 마감했어요.`가 표시돼 제출 자체가 차단됐다.
18. `지금 다시 열기`를 눌러 응답을 재개했다. 운영 카드가 `응답 받는 중`으로 전환되고, 공개 응답 화면에도 이메일·질문·제출 버튼이 다시 나타났다. **수동 마감·재개는 UI와 공개 응답 흐름에서 정상 확인**했다.

## 전용 임시 폼 · E2EE 복호화·내보내기 검증 진행 기록

19. 기존 테스트 폼의 복구 비밀번호를 알 수 없어, 별도 폼 `Cokform E2EE 내보내기 검증 — 삭제 예정`을 생성했다. 이 폼에는 감사용 임시 복구 비밀번호와 비식별 이메일 `e2ee.audit@example.com`만 사용했다.
20. 새 폼에서 PBKDF2 기반 개인키 금고 생성 후 공개 응답 페이지로 이동해 이메일과 객관식 선택지를 제출했다. 완료 화면 `응답이 저장되었습니다`가 표시됐다.
21. 홈 운영 현황은 폼 2개·응답 2건으로, 임시 폼의 응답 1건을 집계했다. 금고가 잠긴 상태에서 답변 탭은 다시 잠금 해제를 요구했고, 올바른 임시 비밀번호로 열자 답변 탭 배지 `1`, 기록된 이메일 카드, 객관식 집계가 표시됐다. **새 키 생성 → 암호화 제출 → 세션 잠금 → 같은 키로 복호화** 흐름은 정상 확인했다.
22. 답변 탭에서 CSV와 Excel 내보내기를 실행했다. 다운로드 산출물의 파일 구조·내용 검증은 다음 단계에서 수행한다.

23. 첫 CSV·Excel 버튼 클릭 뒤 브라우저 다운로드 폴더에는 새 파일이 보이지 않았다. 내보내기 코드에는 Blob URL을 생성하고 앵커 클릭 직후 URL을 해제하는 경로가 있어, 호환성을 위해 URL 해제를 60초 뒤로 늦춘 수정(`9f844ec`)을 배포했다.
24. 배포 뒤 임시 폼을 다시 열어 금고를 해제하고 CSV 내보내기 핸들러를 계측했다. 핸들러는 `text/csv;charset=utf-8` Blob(149 bytes)을 만들고 기대한 파일명으로 다운로드 앵커를 호출했다. 다만 이 자동화 브라우저의 클릭은 해당 핸들러를 다시 호출하지 않으며 다운로드 폴더에도 새 파일을 남기지 않아, **실제 사용 브라우저의 파일 저장 완료는 현재 환경에서 판정 보류**다. 클릭 핸들러와 Blob 생성까지는 확인했고, URL 조기 해제 위험은 수정·배포했다.

> 내보내기 판정: CSV·Excel의 데이터 구성 및 다운로드 호출은 확인했으나, 자동화 환경의 Blob 다운로드 제약으로 실제 파일 저장 완료는 수동 Chrome 재확인이 필요하다. Google Drive·Sheets 직접 전송은 사용자 Google 권한을 새로 부여하는 외부 작업이므로 이번 자동 감사에서 실행하지 않았다.

25. **암호화 키 백업 검증 통과**: 임시 키 백업 Blob(711 bytes)을 값 노출 없이 구조 검사했다. `formId` 일치, `vault` 기반 구조, salt·iv·ciphertext는 존재하고, JWK 평문 개인키 필드 `d`는 없었다.
26. **전체 복구 번들 검증 통과**: 임시 복구 번들 Blob(7,578 bytes)은 `format`, `version`, `formId`, `exportedAt`, `keyVault`, `data`만 최상위에 두며 salt·iv·ciphertext를 포함했다. 비식별 이메일과 선택 응답 문자열은 번들 평문에 존재하지 않았고 JWK `d`도 없었다.
27. **P1 · 버전 복원 확인창의 위험한 오표기**: 이전 버전으로 복원하려고 하면 실제 동작 설명은 복원이지만 확인 버튼이 빨간색 `삭제`로 표시됐다. 사용자는 복원을 포기하거나 잘못된 작업으로 오인할 수 있다. 임시 폼에서는 취소했고, 코드에서 버전 작업에만 초록색 `복원` 버튼을 보여주도록 수정·빌드 검증했다. 배포 및 운영 재확인은 다음 단계에서 진행한다.
28. 버전 기록은 잠금 해제된 금고에서 자동 저장 1건과 최초 저장 1건을 정상 표시했다. 실제 복원 실행은 오표기를 발견한 시점에 취소했으므로, 버튼 수정 배포 뒤 동일한 임시 폼에서 복원 완료까지 재검증해야 한다.

29. **P1 수정 운영 재검증 통과**: 배포된 확인창은 초록색 `복원` 버튼을 표시했고, 이전 버전을 실제 실행한 뒤 `이전 버전으로 복원했습니다.` 안내와 정상 편집기 복귀·저장 상태를 확인했다. 이 P1은 해결됐다.

30. **390px 모바일 공개 응답 화면**: 실제 390×844 캡처에서 제목, 개인정보 안내, 이메일 고지·입력, 첫 필수 질문, 제출 버튼이 가로 넘침 없이 한 열로 배치됐다. 이메일 입력과 제출 버튼의 터치 대상은 충분히 크고, 제출 버튼은 첫 화면 하단에 보인다.
31. **P2 · 긴 개인정보 안내의 첫 화면 점유**: 법정 고지 전문과 이메일 고지가 함께 켜진 폼은 첫 화면 대부분을 차지해 첫 질문이 하단에 걸친다. 필수 고지를 숨기면 안 되므로, 기본은 유지하되 모바일에서 `자세히 보기` 접기와 동의 전 전체 보기 접근성을 함께 제공하는 방식이 더 낫다.

32. **390px 모바일 로그아웃 홈**: 로고·Google 로그인·검색·로그인 안내가 첫 화면에 잘 보이고, 공개 응답 링크는 로그인 없이 열린다는 문구도 명확하다.
33. **P1 · 모바일 템플릿 캐러셀의 가로 스크롤바 노출**: 시작 템플릿 카드가 화면을 넘기며 기본 브라우저 가로 스크롤바가 그대로 보인다. 다음 카드가 일부 보이지만 스와이프 안내·페이지 점·화살표가 없어 가로 탐색성도 낮다. 얇은 스크롤바를 숨기고, 카드 스냅·첫 카드 폭 조정·`옆으로 넘겨보기` 힌트를 적용해야 한다.

34. 모바일 템플릿 캐러셀 P1은 기본 스크롤바를 숨기고, 두 템플릿 행에 `옆으로 넘겨 더 보기` 힌트와 스냅 탐색을 유지하는 방식으로 수정했다. 프로덕션 빌드는 통과했으며 배포 뒤 390px 재검증이 필요하다.

35. **모바일 템플릿 탐색 P1 운영 재검증 통과**: 배포 뒤 390px 캡처에서 기본 가로 스크롤바는 사라졌고, 두 템플릿 행 모두 `옆으로 넘겨 더 보기` 힌트가 보여 스와이프 가능한 카드 행임을 명확히 알린다.
36. 커버 이미지 URL 입력도 임시 폼에서 `https://cokform.pages.dev/og-image.png`로 저장해 카드 미리보기에 정상 표시되는 것을 확인했다. 파일 업로드 입력은 자동화 환경에서 숨김 파일 선택기를 안정적으로 조작할 수 없어 이번 기록에서는 URL 저장 경로만 통과 처리한다.

37. 감사에 사용한 `Cokform E2EE 내보내기 검증 — 삭제 예정`, `콕폼 UX 전수 테스트 — 삭제 예정`과 각각의 비식별 응답을 삭제했다. 홈 운영 현황은 만든 폼 0개·전체 응답 0건으로 갱신됐다.
38. **P1 · 삭제된 폼의 참여 이력 잔존**: 폼과 응답을 삭제한 뒤에도 `내가 참여한 폼`에는 제목·문항 수·참여 시각 메타데이터가 남아 `공개 폼 다시 보기`를 제공한다. 삭제된 링크는 유효하지 않아 혼란을 주고, 감사용 메타데이터도 남는다. 폼 삭제 시 해당 폼의 참여 이력을 정리하거나, 존재하지 않는 폼임을 감지해 이력에서 자동 제거해야 한다.

39. 참여 이력 잔존 P1은 `deleteFormDoc`이 성공한 원격 삭제 뒤에도 이 기기의 편의 메타데이터를 같은 form ID 기준으로 정리하도록 수정했다. 계정 동기화 이력은 기존 데이터베이스 외래키의 `ON DELETE CASCADE`로 정리되고, 로컬 이력도 함께 제거된다. 프로덕션 빌드는 통과했으며 배포 뒤 새 임시 폼으로 재검증해야 한다.
