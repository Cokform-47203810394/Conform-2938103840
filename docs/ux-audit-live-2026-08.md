# Cokform 실사용 전수 테스트 기록 · 2026-08-18

## 테스트 환경

- 운영 URL: https://cokform.pages.dev
- 제작자 계정: 사용자 제공 Google 로그인 세션
- 테스트 폼: 빈 양식으로 새 폼 1개 생성. 모든 테스트 데이터는 비민감한 감사용 값만 사용하고, 종료 후 삭제 대상이다.

## 제작자 진입 흐름

1. Google 로그인은 정상 완료됐고, 홈의 제작자 상태·템플릿·운영 현황이 표시됐다.
2. `빈 양식`을 누르면 새 편집기와 개인키 금고 모달이 열렸다.
3. 12자 이상 복구 비밀번호를 두 번 입력한 뒤 개인키 금고 생성은 정상적으로 완료됐다.
4. 금고 설정 중에는 편집기 본문이 `불러오는 중…`으로 막힌다. E2EE 안전성에는 타당하지만, 처음 온 제작자에게는 왜 먼저 복구 비밀번호를 정해야 하는지와 백업을 언제 내려받아야 하는지 안내가 더 짧고 강하게 필요하다.
5. 편집기 진입 직후 첫 제목 입력 시 브라우저 입력 도구에서 일시적 연결 오류가 한 번 발생했다. 화면을 다시 확인하자 동일 입력 제어는 유지돼 있었으며, 제품 오류인지 테스트 브라우저 전송 오류인지는 이후 재현으로 판정한다.

## 다음 검증

폼 제목·설명·질문 유형·필수값·운영 설정·공유를 설정한 뒤 별도 공개 응답자 흐름에서 실제 제출을 진행한다.
6. 제목 입력은 첫 시도에서 브라우저 입력 전송 오류가 있었고, 좌표 기반 입력도 실제 값 반영이 확인되지 않았다. 이후 같은 제목 필드를 요소 기준으로 다시 입력하자 정상 반영되고 `저장 중…` 상태가 표시됐다. 이 테스트 도구의 일시적 입력 전송 문제일 가능성이 높지만, 제작자 UI는 제목 입력 후 저장 완료 상태가 짧게 표시돼 실제 저장 완료를 확인하기 어렵다.
7. 첫 문항 제목 영역을 좌표 방식으로 입력하려 했으나 값이 반영되지 않았다. 화면 자동화가 문항 제목을 표준 input·textarea·contenteditable 제어로 식별하지 못했고, DOM 탐색에서도 질문 플레이스홀더를 찾지 못했다. 실제 사람이 클릭해 입력 가능한지 소스 구조와 미리보기로 추가 재현이 필요하다. 이대로라면 자동화 접근성뿐 아니라 키보드·보조기기 호환성 위험 신호다.
8. 소스 확인 결과 문항 제목은 `contentEditable` 기반 리치 텍스트 편집기다. 포커스 없이 자동화 입력하면 실패했지만, 실제 편집 영역을 클릭한 뒤 입력하자 정상 반영됐다. 서식 도구가 포커스 시에만 떠서 제목 입력과 서식 기능 자체는 동작한다.
9. 첫 문항을 `단답형`으로 전환하고 `필수 입력` 토글을 켰다. 문항 제목은 보존됐고 유형 전환·토글 반영·자동저장은 정상으로 확인됐다. 다만 콘텐츠 편집형 제목이 일반 입력 필드처럼 명확한 테두리·레이블을 주지 않아 처음 쓰는 제작자는 클릭 가능 영역을 놓칠 수 있다.
10. 우측 빠른 추가의 `객관식 질문 추가`는 즉시 Q02를 생성했다. 리치 텍스트 제목에 실제 질문을 입력하고 첫 옵션을 `행사 신청`으로 바꾸는 흐름도 성공했다.
11. 문항 제목 편집은 포커스 뒤에만 입력되는 `contentEditable`이라 일반 텍스트 필드보다 조작 진입점이 약하다. 제작자 UI 자체 기능은 동작했지만, 접근성·자동화 친화성은 낮은 편으로 P1 개선 후보로 기록한다.
12. `개인정보 동의 질문 추가`는 수집 목적·수집 항목·보유 기간·거부권 안내·동의/미동의 선택지·미동의 제출 차단 토글을 한 번에 생성했다. 미동의 제출 차단 토글도 켜졌다. 기본 문구는 바로 쓸 수 있는 수준이나, 실제 운영자가 자기 조직·목적·기간에 맞춰 모든 항목을 수정해야 한다는 경고가 카드 내부에 더 분명히 보여야 한다.
13. 객관식 두 번째 옵션 추가·수정도 정상 동작했다.

## 운영 설정·공유 검증

14. 이메일 주소 기록, 개인정보 수집 안내, 응답자 사본 안내, 응답 기간 설정은 작성자 설정 화면에서 확인했다. 테스트 폼에는 이메일 기록과 개인정보 안내, 응답자 사본 표시가 켜져 있었고 공개 응답 화면에 각각의 고지와 필수 이메일 입력이 노출됐다.
15. 공유 링크 생성과 공개 응답 화면 로드는 정상으로 확인됐다. 응답자는 작성자 설정에 따라 개인정보 수집 안내, 이메일 기록 고지, 필수 항목, 미동의 제출 제한 안내를 확인할 수 있었다.

## P0 · 공개 응답 제출 실패 — 수정 및 재검증 완료

| 항목 | 결과 |
|---|---|
| 증상 | 공개 응답 화면에서 유효한 비식별 테스트 데이터를 제출하면 `POST /rest/v1/responses`가 HTTP 400으로 실패했다. 화면은 원인을 `네트워크` 문제로만 표시했다. |
| 실제 원인 | 배포된 `public.responses` 테이블에 클라이언트가 항상 전송하는 `respondent_token` 컬럼이 없었다. 클라이언트 코드와 실제 스키마가 어긋나 PostgREST가 요청 본문을 거절했다. |
| 조치 | `20260818_restore_response_token_column.sql` 마이그레이션으로 nullable `respondent_token`과 부분 고유 인덱스를 멱등 방식으로 복구했다. 트리거 함수의 `anon` 실행 권한은 필요하지 않았으며, 보안상 재부여하지 않았다. |
| 재검증 | 같은 테스트 폼에서 재제출 후 `응답이 저장되었습니다` 완료 화면을 확인했다. 운영 현황의 응답 수가 1건으로 갱신됐고, DB에는 응답 원문을 읽지 않은 상태로 제출 시각·만료 시각만 확인했다. 만료 시각은 설정된 180일 보관 기간과 일치한다. |

> P0 상태: **해결됨**. 이슈는 브라우저 네트워크가 아니라 실제 운영 DB의 스키마 누락이었다. 이후에는 마이그레이션 적용 확인을 릴리스 체크리스트에 넣어야 한다.

## P1 · 잠긴 개인키 금고가 폼 편집 전체를 막음 — 수정 진행

폼을 다시 열어 개인키 금고가 잠긴 경우, 기존 구현은 폼 구조까지 불러오지 않고 금고 모달을 닫을 수도 없었다. 응답 평문과 암호화 버전은 금고 잠금 상태에서 보호해야 하지만, 제목·질문·설정처럼 응답 원문이 아닌 폼 구조까지 편집 불가로 만드는 것은 제작자 자유도와 운영 연속성을 크게 떨어뜨린다.

수정안은 잠긴 상태에서도 폼 구조만 로드하고 응답·복호화된 버전은 빈 상태로 유지하는 것이다. 답변 탭과 버전 기록을 열 때만 금고 해제를 요구하고, 응답 암호화 키가 없는 새 폼은 공개 공유·링크 복사를 막는다. 잠긴 금고 모달도 사용자가 닫을 수 있어야 한다. 이 변경은 로컬 빌드를 통과했으며, 배포 뒤 재검증한다.
