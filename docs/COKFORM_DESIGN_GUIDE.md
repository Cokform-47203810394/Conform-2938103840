# Cokform 제품 디자인 가이드

이 문서는 Cokform의 웹·모바일 화면을 구현하고 검수할 때 사용하는 실무 기준입니다. 브랜드 가이드가 “Cokform답게 보이는가”를 다룬다면, 이 문서는 “Cokform답게 작동하는가”를 다룹니다.

## 1. 기본 원칙

Cokform의 UI는 폼을 만드는 사람과 응답하는 사람이 서로 다른 목적을 가진다는 사실에서 출발합니다. 작성자는 빠르게 구조를 만들고 수정해야 하며, 응답자는 설명을 이해하고 답변을 잃지 않은 채 제출해야 합니다. 운영자는 응답 상태·알림·복구를 한눈에 확인해야 합니다.

| 원칙 | 구현 기준 |
|---|---|
| 질문이 먼저 | 제목·설명·필수 여부·응답 입력을 장식보다 우선 배치 |
| 한 화면 한 행동 | 대표 CTA를 하나로 정하고 보조 행동은 시각적 무게를 낮춤 |
| 상태는 즉시 | 저장됨·오류·마감·초안 복구 상태를 짧은 문장과 아이콘으로 표시 |
| 되돌릴 수 있게 | 삭제·초기화·마감은 확인과 복구 경로를 함께 제공 |
| 조건은 조용하게 | 조건부 문항은 필요한 시점에만 나타내고 다른 팀 질문을 섞지 않음 |
| 모바일 우선 | 390px에서 가로 스크롤 없이 읽고 입력할 수 있어야 함 |
| 개인정보는 명확하게 | 수집 목적·항목·보유 기간·동의·책임 주체를 폼 안에서 확인 가능하게 함 |

## 2. 디자인 토큰

### 2.1 색상 토큰

코드에서는 `src/theme.js`와 `src/index.css`의 값을 우선 사용합니다. 새 색상을 추가하기 전에 기존 의미 토큰으로 표현할 수 있는지 확인합니다.

```css
:root {
  --cok-ink: #17251f;
  --cok-deep-green: #0f5b46;
  --cok-green: #17866d;
  --cok-leaf: #73b99d;
  --cok-mint: #d8f5e8;
  --cok-warm-white: #fffdf8;
  --cok-canvas: #f5f3ec;
  --cok-line: #dde1d9;
  --cok-error: #b94a48;
}
```

`#17866D`는 상태·링크·선택 신호로 사용하고, 작은 흰 글자 버튼의 배경은 `#0F5B46`을 사용합니다. 색상 대비를 조정할 때는 모양과 문구를 바꾸지 않고 의미 토큰만 바꿉니다.

### 2.2 타이포그래피

Cokform은 Pretendard를 기본 글꼴로 통일합니다. 숫자·응답 건수·페이지 번호에도 별도 숫자 폰트를 적용하지 않습니다. 숫자는 데이터의 일부이며 장식이 아니므로 본문과 같은 글꼴 체계를 유지합니다.

| 역할 | 권장 스타일 | 용도 |
|---|---|---|
| Display | Pretendard Bold, 짧은 행, 강한 대비 | 랜딩 히어로·페이지 제목 |
| H1 | Pretendard Bold | 화면의 단일 제목 |
| H2 | Pretendard Bold 또는 Semibold | 섹션 제목 |
| H3 | Pretendard Semibold | 카드·문항 제목 |
| Body | Pretendard Regular, 16px 기준 | 설명·질문·응답 |
| Caption | Pretendard Regular, 12~13px | 날짜·보조 상태·힌트 |
| Label | Pretendard Medium, 13~14px | 필드 라벨·필수 표시 |
| Number | Pretendard Regular 또는 Medium | 건수·페이지·선택값 |

제목은 필요 이상으로 `font-semibold`를 반복하지 않습니다. 본문과 캡션에 세미볼드를 섞어 계층을 흐리지 말고, 강조가 필요하면 굵기보다 색상·간격·위치를 먼저 조정합니다.

### 2.3 간격·모서리·그림자

기본 간격은 4px 단위를 사용하되, 화면의 주요 여백은 8·12·16·24·32px에서 선택합니다. 카드와 입력 영역의 모서리는 일관되게 유지하고, 하나의 화면에 3종 이상의 radius를 섞지 않습니다.

| 토큰 | 값 | 사용 |
|---|---:|---|
| `space-1` | 4px | 아이콘과 짧은 텍스트 |
| `space-2` | 8px | 라벨·힌트 간격 |
| `space-3` | 12px | 컨트롤 내부 |
| `space-4` | 16px | 카드 내부 기본 |
| `space-6` | 24px | 카드·섹션 간격 |
| `space-8` | 32px | 큰 섹션 간격 |
| `radius-sm` | 8px | 작은 태그·셀렉트 |
| `radius-md` | 12px | 입력·버튼·카드 |
| `radius-lg` | 16px | 주요 카드·모달 |

카드는 기본적으로 1px 경계와 평면 표면을 사용합니다. 그림자는 `ELEV1` 하나를 기본으로 하고, 드롭다운·모달처럼 콘텐츠가 떠야 하는 경우에만 `ELEV2` 이상을 사용합니다. 카드마다 다른 그림자·테두리 두께·radius를 적용하지 않습니다.

## 3. 컴포넌트 규칙

### 3.1 버튼

버튼 문구는 동작과 결과를 함께 말합니다. `저장`, `제출`, `폼 만들기`, `응답 보기`처럼 사용자가 다음 결과를 예측할 수 있어야 합니다. 아이콘만 있는 버튼에는 `aria-label`과 툴팁을 제공합니다.

| 종류 | 시각 규칙 | 사용 상황 |
|---|---|---|
| Primary | Deep Green 배경·흰 글자 | 화면의 대표 행동 |
| Secondary | Warm White 또는 투명·경계 | 보조·취소·이전 |
| Tertiary | 배경 없음·텍스트 링크 | 저강도 탐색 |
| Destructive | 오류 토큰·명확한 확인 | 삭제·영구 초기화 |
| Success | Mint 배경·Deep Green 글자 | 저장됨·복구됨 상태 |

버튼은 hover에서 위치·크기를 바꾸지 않습니다. `transform`으로 경계가 이동하면 포인터가 반복 진입하는 jitter가 발생할 수 있으므로 색상·그림자·outline만 변경합니다. 터치 환경에서는 실질적인 클릭 영역을 최소 44px 높이로 확보하고, WCAG 2.2의 최소 포인터 대상 크기 24×24px보다 넉넉하게 설계합니다. [1]

### 3.2 카드

카드는 정보를 그룹화하는 용도로만 사용합니다. 카드 안에 또 다른 카드가 반복되는 구조는 설정·리소스 선택처럼 사용자가 단계를 구분해야 할 때만 허용합니다.

카드에는 제목, 필요한 경우 짧은 설명, 대표 행동 순서로 배치합니다. 제목보다 장식 아이콘을 크게 만들지 않으며, 카드 전체가 클릭 가능할 때만 전체를 링크로 만듭니다. 클릭 불가능한 카드는 hover 효과를 넣지 않습니다.

### 3.3 입력과 질문

입력 필드에는 질문 제목, 필수 여부, 설명 또는 글자 수 조건, 입력 영역을 순서대로 둡니다. placeholder에 질문 자체나 필수 안내를 넣지 않습니다. 오류 문구는 입력 필드 아래에 원인과 해결 방법을 함께 표시합니다.

긴 서술형 질문은 textarea를 사용하고, 줄바꿈을 보존합니다. Enter를 입력했을 때 한 줄로 합쳐지지 않아야 하며, `white-space: pre-wrap`과 적절한 `line-height`를 유지합니다. 리치 텍스트는 저장·미리보기·응답 화면에서 같은 줄바꿈 규칙을 사용합니다.

필수 문항은 색상만으로 표시하지 않고 `필수` 텍스트와 `aria-required="true"`를 함께 제공합니다. 팀 선택에 따라 나타나는 질문은 숨겨진 질문의 값이 제출 데이터에 포함되지 않도록 정리합니다.

### 3.4 상태·알림

상태는 “무슨 일이 일어났는지”와 “지금 무엇을 할 수 있는지”를 한 줄에 표현합니다.

| 상태 | 권장 문구 | 다음 행동 |
|---|---|---|
| 저장 중 | 저장하는 중입니다 | 기다림 |
| 저장됨 | 방금 저장됨 | 계속 작성 |
| 초안 복구 | 이전 작성 내용을 복구했습니다 | 이어서 작성 또는 삭제 |
| 마감 | 현재 응답을 받지 않습니다 | 작성자에게 문의 |
| 오류 | 저장하지 못했습니다 | 다시 시도·복구 |
| 보안 확인 | 안전한 응답 제출을 확인하는 중입니다 | 잠시 기다림 |

토스트만으로 중요한 오류를 전달하지 않습니다. 페이지 안의 `aria-live="polite"` 또는 오류 영역에 같은 내용을 남겨 새로고침·스크린 리더·모바일 환경에서도 확인할 수 있게 합니다.

## 4. 화면별 구성

### 4.1 폼 편집기

편집기는 왼쪽 또는 상단에 폼 구조, 중앙에 현재 질문, 가까운 위치에 추가 행동을 둡니다. 질문 제목을 클릭하면 즉시 편집되고, 포커스를 훔치는 자동 선택 로직을 넣지 않습니다. 저장 중에는 입력을 막지 않으며, 페이지를 이동하거나 새로고침해도 마지막 유효 버전이 복구되어야 합니다.

질문 추가는 화면 가장자리의 작은 버튼만 의존하지 않습니다. 현재 질문 옆에 `질문 추가`, `설명 추가`, `섹션 추가`를 바로 제공하고, 키보드 사용자는 Tab 순서만으로 접근할 수 있게 합니다. 삭제는 즉시 제거하되 undo 또는 휴지통에서 되돌릴 경로를 제공합니다.

### 4.2 응답자 화면

응답자 화면은 로그인 없이 열리는 공개 폼이라는 사실을 첫 화면에서 방해 없이 이해할 수 있어야 합니다. 제목·설명·개인정보 수집 안내·이메일 기록 여부·질문 순서가 자연스럽게 이어져야 하며, 불필요한 운영자 기능을 노출하지 않습니다.

응답 입력은 새로고침·탭 전환·일시적 네트워크 끊김을 고려해 로컬 초안을 유지합니다. 초안은 폼별·브라우저별로 분리하고, 복구 사실과 삭제 방법을 응답자에게 알려야 합니다. 테스트 문구나 장난성 응답 방지 안내는 공격적인 표현보다 제출 기준을 구체적으로 안내합니다.

### 4.3 운영 화면

운영 화면은 개별 응답을 한 덩어리로 보여줍니다. 질문별 데이터를 별도 탭으로 분리해 사용자가 응답자의 맥락을 잃게 만들지 않습니다. 검색·상태 필터·개별 삭제·전체 삭제는 같은 응답 목록 안에서 작동하고, 삭제 후에는 즉시 피드백과 복구 경로를 표시합니다.

## 5. 반응형 기준

| 구간 | 기준 |
|---|---|
| 0~479px | 단일 열, 카드 내부 패딩 16px, 큰 제목은 2~3줄까지 허용 |
| 480~767px | 단일 열 중심, 보조 정보만 2열 허용 |
| 768~1023px | 편집기·문서 화면은 2열을 검토하되 입력 폭을 우선 |
| 1024px 이상 | 콘텐츠 최대 폭을 제한하고 주변 여백으로 호흡 확보 |

모바일에서 버튼은 서로 붙이지 않으며, 가로로 긴 테이블·코드·다운로드 옵션은 컨테이너 내부에서만 가로 스크롤하도록 합니다. 페이지 전체에 가로 스크롤이 생기면 실패입니다. 긴 한국어 제목은 임의로 자르지 말고 자연스러운 줄바꿈을 허용합니다.

## 6. 접근성 체크

Cokform은 색상·폰트·장식보다 정보의 이해 가능성을 우선합니다. 일반 텍스트는 최소 4.5:1, 큰 텍스트는 최소 3:1 대비를 목표로 하며, 비텍스트 UI 경계와 포커스도 눈에 보여야 합니다. [2]

키보드 Tab 순서를 시각적 순서와 일치시키고, 포커스 링을 제거하지 않습니다. 아이콘 버튼에는 이름을 주고, 라디오·체크박스·필드셋에는 그룹 레이블을 제공합니다. 오류는 색상 외에 문구와 위치로 전달하며, 애니메이션을 줄이기 원하는 사용자를 위해 `prefers-reduced-motion`을 존중합니다.

## 7. 개발 토큰 예시

```js
export const DESIGN = {
  color: {
    ink: "#17251F",
    primary: "#0F5B46",
    action: "#17866D",
    surface: "#FFFDF8",
    canvas: "#F5F3EC",
    line: "#DDE1D9",
    success: "#D8F5E8",
    error: "#B94A48",
  },
  radius: {
    sm: "rounded-lg",
    md: "rounded-xl",
    lg: "rounded-2xl",
  },
  shadow: {
    card: "shadow-[0_2px_4px_rgba(23,37,31,0.06),0_8px_20px_rgba(23,37,31,0.04)]",
  },
};
```

새 컴포넌트는 `Brand Tokens → Semantic Tokens → Component Tokens` 순서로 값을 선택합니다. JSX 안에 목적이 같은 색상 HEX를 반복해서 쓰지 말고 `theme.js` 또는 CSS 변수로 올립니다. Tailwind 클래스를 사용할 때도 컴포넌트의 의미가 드러나는 조합을 우선합니다.

## 8. QA 체크리스트

배포 전에는 데스크톱과 390px 모바일에서 제목·설명·입력·버튼이 겹치지 않는지 확인합니다. 폼 편집기에서는 제목 수정, Enter 줄바꿈, 질문 추가·삭제, 새로고침 후 복구, 이전 버전 복원을 확인합니다. 응답자 화면에서는 조건부 질문, 숨겨진 질문 값 제거, 개인정보 고지, 최소 글자 수, 금칙어, 제출 확인, 초안 복구를 확인합니다. 운영 화면에서는 응답 단위 보기, 검색, 필터, 개별 삭제, 전체 삭제, 알림 삭제, 내보내기와 복구 경로를 확인합니다.

시각 QA에서는 카드 스트로크 두께, radius, 그림자, Pretendard 적용 여부, 숫자 폰트 통일, CTA 우선순위, 포커스 링, 오류 대비, 가로 넘침을 확인합니다. 기능이 정상이어도 같은 화면에서 카드·버튼·문구의 시각 규칙이 흔들리면 릴리스하지 않습니다.
