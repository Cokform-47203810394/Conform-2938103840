# 공공기관 사용자용 보안·데이터 무결성 강화안

작성일: 2026-08-22  
대상: 콕폼 파일럿 운영 환경  
목적: 개인정보·암호화 응답·폼 운영 기록이 실수, 장애, 악성 변경 뒤에도 **마지막 정상 상태로 복원 가능**하고, 변경 사실을 설명할 수 있도록 통제를 강화한다.

> 이 문서는 현재 콕폼이 ISMS-P 인증 또는 특정 공공기관 보안 적합성을 획득했다는 주장이 아니다. 공개 파일럿에서 우선 적용할 통제와, 기관 도입 심사 전에 준비해야 할 증빙 목록을 정리한 실행 계획이다.

## 1. 현재 구현된 기준선

| 영역 | 현재 상태 | 검증 근거 |
|---|---|---|
| 응답 기밀성 | 폼 단위 ECDH P-256/AES-256-GCM E2EE. 개인키는 서버에 전송하지 않음 | 응답 원문은 암호문으로만 저장 |
| 일반 복구 | 버전 기록, 구조 급감 전 암호화 스냅샷, 최소 30일 폼 휴지통 | 폼·응답·버전 통합 롤백 테스트 통과 |
| 재해 복구 | 매일 roles·public schema·Auth data·public data 논리 덤프를 `age` 암호화하고 SHA-256 검증값과 함께 90일 보관 | 2026-08-22 수동 백업·artifact SHA-256 검증 통과 |
| 접근 통제 | Supabase RLS로 폼 소유자 데이터 접근 제한 | 정책·로그 점검 완료 |
| 변경 추적 | 폼 감사 이벤트·Git 커밋·Cloudflare 배포 이력 | 일부 변경 이력은 더 강화 필요 |

## 2. 우선순위 통제

| 우선순위 | 통제 | 구현 또는 운영 방식 | 완료 판정 |
|---|---|---|---|
| P0 | 복구 리허설 | 분기 1회 격리된 Supabase 프로젝트에 암호화 백업을 복호화·복원하고 행 수·RLS·E2EE 복호화까지 확인 | 리허설 기록, 실제 복원 시간, 누락 0건 |
| P0 | 변경 전후 무결성 검증 | 배포 전 DB 마이그레이션 dry-run, 빌드, 핵심 회귀 테스트. 배포 직후 폼 수·응답 수·RLS 정책 요약을 자동 대조 | 실패 시 배포 중단 또는 이전 릴리스로 즉시 롤백 |
| P0 | 휴지통 영구 삭제 분리 | 일반 삭제는 휴지통 이동만 허용. 영구 파기는 30일 이후 별도 권한·재인증·사유·2단계 확인으로 분리 | 응답·버전의 무심코 삭제 0건 |
| P1 | 변경 불가 감사 사본 | 주요 이벤트(폼 생성·휴지통 이동·복원·권한·응답 삭제)를 일 단위 해시 체인으로 묶고 암호문 백업에 포함 | 체인 검증 실패 시 경보 |
| P1 | 별도 오프사이트 암호문 | R2 또는 다른 독립 객체 저장소에 `.age` 파일만 복제. 평문 SQL·개인키는 금지 | 서로 다른 제공자에서 동일 SHA-256 확인 |
| P1 | 관리자 분리 | Cloudflare, Supabase, GitHub의 일상 운영 계정과 긴급 복구 계정을 분리하고 MFA·최소 권한 적용 | 월 1회 권한 검토 기록 |
| P1 | 기관별 데이터 경계 | 기관별 전용 프로젝트 또는 적어도 기관 식별자·RLS·백업 범위를 분리. 기관 A의 운영자가 기관 B 메타데이터도 보지 못하게 설계 | 교차 테넌트 접근 테스트 0건 |
| P2 | 입력·내보내기 악성 콘텐츠 방어 | 파일 기능 도입 전 MIME·크기·악성코드 검사·격리 정책, PPTX/이미지 내보내기 의존성 회귀 점검 | 악성 샘플 테스트 통과 |
| P2 | 사고 대응 체계 | 연락망, 영향 범위 판단, 사용자 통지, 복구 승인, 사후 보고 템플릿을 갖춘 IR 절차 | 연 1회 테이블탑 훈련 |

## 3. 권장 무결성 검증 지표

| 지표 | 목표 | 측정 방식 |
|---|---:|---|
| RPO | 일반 재해 시 24시간 이하 | 마지막 암호화 DB 백업 시각 |
| RTO | 파일럿 기준 4시간 이내 목표 | 분기 복구 리허설의 시작~검증 완료 시간 |
| 휴지통 복원 성공률 | 100% | 휴지통 통합 테스트와 실제 복원 이력 |
| 폼/응답/버전 수 대조 | 배포 전후 0건 비의도 감소 | 배포 검증 쿼리 |
| 감사 기록 검토 | 월 1회 | 휴지통·복원·권한 변경 이벤트 표본 점검 |
| 접근 권한 검토 | 월 1회, 인력 변경 즉시 | Cloudflare·GitHub·Supabase 권한 목록 |

## 4. 기관에 설명할 때의 정확한 표현

콕폼은 응답 원문을 폼 작성자의 기기 키로 암호화하는 E2EE 구조를 채택하고, 일반 삭제를 복원 가능한 휴지통으로 전환했으며, 일일 암호화 백업과 복구 절차를 운영한다. 다만 **ISMS-P 인증·공공기관 보안 적합성 인증을 취득했다고 표현해서는 안 된다.** 기관별 계약·개인정보 처리위탁·국외 이전·보유기간·접근권한·보안성 검토 요건은 별도 확인이 필요하다.

## 5. 근거

개인정보의 안전성 확보조치 기준은 접근권한 관리, 접속기록 보관·점검, 암호화 조치 등 내부 관리계획 이행 실태를 정기 점검하도록 규정한다.[1] KISA는 ISMS-P를 정보보호 및 개인정보보호를 위한 일련의 조치와 활동이 인증 기준에 적합함을 증명하는 제도로 설명한다.[2] NIST의 데이터 무결성 가이드는 마지막 정상 상태 복원, 변경 시점·주체 식별, 감사·보고 기록을 핵심 목표로 든다.[3] CISA는 중요 데이터의 오프라인 암호화 백업과 정기적인 복구 가능성·무결성 시험을 권고한다.[4]
