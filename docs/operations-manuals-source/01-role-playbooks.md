# 역할별 실전 플레이북

> 이 문서는 2,000개 세부 매뉴얼의 ‘어떤 역할이 무엇을 판단하는가’를 먼저 정한다. 역할이 겹치면 **사용자 답변·개인키·권한에 가장 가까운 사람이 혼자 판단하지 않는다.** 보안·개인정보·배포 영향은 대표 또는 책임자에게 기록으로 남긴다.

## 역할 한눈에 보기

| 코드 | 역할 | 매일 확인할 것 | 산출물 | 즉시 중단할 조건 |

| GOV | 창업가 | 이번 주 사용자 증거, 비용, 위험 | 우선순위 결정 기록 | 증거 없는 기능 확장 |
| PRD | 기획가 | 사용자 문제, 가설, 성공 조건 | 문제·가설 카드 | ‘왜’를 말할 수 없는 요청 |
| UXD | 디자이너 | 정보 위계, 모바일, 접근성 | 화면 검토 메모 | 색·굵기만으로 의미 전달 |
| FEN | 프런트엔드 개발자 | 빌드, 오류 경계, 핵심 화면 | PR·검증 기록 | 빌드 실패·렌더링 오류 |
| BEN | 백엔드 개발자 | RLS, RPC, 마이그레이션 | 변경·롤백 기록 | 권한 검증 없는 DDL/DML |

| QAT | QA 엔지니어 | 핵심 5경로, 회귀 | 테스트 결과 | 재현되지 않은 버그 종료 |

| DAT | 데이터 운영자 | 보관·파기·백업 | 보관·복구 기록 | 복구 검증 없는 백업 선언 |
| SUP | 고객지원 | 민감정보 없는 문의 해결 | 문의 분류·해결 기록 | 답변 원문·키 요청 |
| LEG | 개인정보 담당자 | 고지·수집 최소화·역할 | 점검표 | 동의 없이 민감정보 테스트 |

| SEO | 콘텐츠 담당자 | 검색 의도·가이드 최신성 | 콘텐츠 갱신 기록 | 키워드만 있고 해결책 없는 글 |

| SAL | 컨시어지 운영자 | 더미 데이터·지원 범위 | 테스트 메모 | 실제 신청자 원문 수령 |
| PEO | 협업 책임자 | 최소 권한·산출물·회수 | 권한·브리프 기록 | 개인 계정 무단 공유 |
| RES | 리서처 | 출처·사용자 문제·대체 수단 | 의사결정 연결 메모 | 경쟁사 기능 목록만 복사 |
| BCP | 위기 대응 책임자 | 사고 영향·공지·복구 | 타임라인·사후 회고 | 추측을 사실처럼 공지 |

## GOV · 창업가

매주 월요일에는 ‘지난 7일에 실제로 사용자가 한 행동’을 먼저 읽는다. 기능 수, 커밋 수, 디자인 완성도보다 폼 생성·공유·재사용·명확한 거절 이유가 우선이다. 새 요청은 `문제 / 대상 사용자 / 성공 신호 / 하지 않았을 때 손실` 네 문장이 채워질 때만 다음 단계로 보낸다.

**결정 기준:** 사용자 증거가 없는 기능은 아이디어로만 보관한다. 이미 만든 기능도 재사용이 없고 흐름을 복잡하게 하면 제거 후보로 표시한다. 비용이 월 1만 원 기준을 넘길 가능성이 있으면 기능 가치보다 먼저 비용 근거를 확인한다.

## PRD · 기획가

기능 요청을 받을 때 ‘무엇을 만들까요?’ 대신 ‘사용자가 어느 순간에 멈추나요?’부터 묻는다. 인터뷰에는 실제 최근 업무를 한 번 재현하게 하고, 희망 기능보다 현재 쓰는 우회 방법을 기록한다. 가설은 한 사용자군·한 행동·한 성공 신호만 포함한다.

**완료 정의:** 구현·배포는 가설의 시작이다. 대상 사용자 3명 이상이 실제 업무에 사용하거나, 쓰지 않은 구체적 이유가 기록돼야 검증 완료다.

## UXD · 디자이너

화면을 검토할 때 모든 정보를 카드에 넣지 않는다. 작업 선택은 작업대, 수치는 정보 행, 기록은 목록, 위험은 상태선처럼 역할을 나눈다. 굵기는 제목·결정·상태에만 쓰며 숫자와 본문은 Pretendard로 일관되게 읽혀야 한다.

**접근성 기준:** 색상만으로 질문 유형·상태·오류를 구분하지 않는다. 유형명, 아이콘, 텍스트 상태 중 하나를 함께 둔다. 키보드 포커스, 320px 화면, 긴 한글 이름, 오류 상태를 반드시 확인한다.

## FEN · 프런트엔드 개발자

변경 전에는 영향 화면, 기존 상태, 되돌릴 커밋을 적는다. React 렌더 오류는 전역 오류 경계와 공개 응답 오류 경계가 잡아야 하며, 새 화면도 빈 데이터·느린 로딩·권한 없음에서 정상 문구를 보여야 한다. `npm run build`가 통과해도 운영 배포가 성공한 것은 아니다.

**배포 전 최소 경로:** 홈 열기 → 로그인 상태 확인 → 폼 열기 → 질문 편집 → 미리보기 → 공개 응답 링크 → 제출 오류 안내를 확인한다. 민감한 실제 답변으로 테스트하지 않는다.

## BEN · 백엔드 개발자

스키마 변경은 반드시 마이그레이션 파일로 만들고, RLS와 RPC 호출 권한을 같이 검토한다. 서비스 역할 키가 필요한 작업은 Edge Function 내부로 제한하며 프런트엔드로 보내지 않는다. `SELECT *`와 범위 없는 조회는 운영 진단에 사용하지 않는다.

**중단 기준:** 롤백 SQL, 백업, 영향 테이블을 모르면 변경하지 않는다. 응답 암호문 또는 키 관련 행을 수동 수정해야 한다면 보안 책임자와 함께 원인을 먼저 분리한다.

## SEC · 보안 담당자

개인키는 브라우저에서만 복호화되고 서버에는 공개키·암호문만 남는다는 경계를 문서·코드·지원 과정에서 일관되게 지킨다. 비밀번호를 잊었을 때 데이터는 보관되지만 서비스가 비밀번호 재설정으로 답변을 열어주지 않는다. 복구는 백업 파일·복구 번들·기존 기기처럼 사용자가 가진 수단으로만 가능해야 한다.

**비밀 관리:** GitHub Secrets, Supabase Secrets, Cloudflare 토큰은 화면·채팅·로그·문서에 남기지 않는다. 노출 의심 시 기능 개발을 멈추고 교체, 영향 범위 확인, 감사 기록 순서로 간다.

## QAT · QA 엔지니어

테스트는 현재 가장 중요한 사용자 경로부터 만든다. 첫 묶음은 로그인, 폼 생성, 질문 추가·저장, 공개 링크 열기, E2EE 제출 오류 처리, 개인키 없는 응답 열람 차단이다. 버그는 재현 조건·기대 결과·실제 결과·환경을 민감정보 없이 기록한다.

**종료 기준:** 수정자가 ‘고쳤다’고 말하는 것이 아니라, 같은 재현 절차에서 실패가 사라지고 인접 경로가 깨지지 않았음을 확인해야 닫는다.

## OPS · 운영 담당자

배포는 GitHub Actions가 성공한 뒤 Cloudflare Pages 운영 URL을 새 쿼리 문자열로 열어 확인한다. 화면이 하얗거나 공개 응답 링크가 열리지 않으면 추가 기능 배포를 멈추고, 마지막 정상 커밋·브라우저 오류·배포 로그를 비교한다.

**장애 공지:** 원인 추측을 공지하지 않는다. 영향을 받은 기능, 사용자에게 필요한 행동, 다음 업데이트 시각만 쓴다. 응답 원문·IP·비밀값을 사고 기록에 넣지 않는다.

## DAT · 데이터 운영자

응답 보관 기간, 자동 파기, 암호화 백업, 복구 테스트는 세트다. 백업 파일이 만들어졌다는 것만으로는 백업이 아니다. 분리된 환경 또는 복구 흐름에서 열리는지 확인해야 한다. 내보낸 CSV·Excel은 생성자 기기에서 별도 개인정보 관리 대상임을 안내한다.

**삭제:** 응답 원문을 직접 살펴보지 않고 ID·보관 정책·소유권 기준으로 삭제한다. 파기 전에는 요청 근거와 영향 범위를 기록한다.

## SUP · 고객지원

지원은 사용자가 해결하도록 돕는 일이지 비밀을 받는 일이 아니다. 문의에 필요한 최소 정보는 폼 ID, 발생 시각, 브라우저, 오류 문구, 민감정보가 가려진 화면이다. 개인키·복구 비밀번호·키 백업·응답 원문은 받지 않고, 사용자가 자신의 기기에서 처리하게 안내한다.

**분류:** 로그인/공유/제출/복구/내보내기/버그/보안 제보로 분류한다. 보안 제보는 일반 문의와 섞지 않고 SEC에 즉시 전달한다.

## LEG · 개인정보 운영 담당자

폼 운영자가 수집 목적·항목·보유 기간을 자기 상황에 맞게 고지하도록 돕는다. 콕폼 플랫폼 정책과 각 폼 운영자의 책임을 섞지 않는다. 채용·의료·금융·미성년자·민감정보는 일반 파일럿에서 제외한다.

**컨시어지:** 양식 구조와 설정만 더미 데이터로 지원한다. 실제 신청자 원문, 첨부, 연락처를 콕폼 운영자가 직접 받는 방식은 금지한다. 실제 역할·위탁 여부·계약은 공개 운영 전에 전문가 검토를 받는다.

## FIN · 비용 담당자

매월 Cloudflare, Supabase, 도메인, 이메일, 분석 도구를 한 표로 확인한다. 무료 한도는 ‘이달 사용량’과 ‘한도 초과 시 서비스 영향’을 같이 기록한다. 사용자가 없는데 유료 도구를 늘리지 않는다.

**승인:** 월 1만 원을 넘길 가능성이 있는 고정비는 사용자 검증 근거와 중단 기준을 함께 적어야 한다.

## MRK · 마케터

콕폼은 디스코드 전용 도구가 아니라 행사·교육·커뮤니티 운영자가 신청을 받고 확인하고 마감하는 한국 실무용 폼이다. 모든 카피는 실제 사용 장면 하나를 말해야 한다. ‘완벽한 보안’ 같은 절대 표현 대신 작성자만 자신의 키로 읽도록 설계됐다는 검증 가능한 표현을 쓴다.

**브랜드 문장:** `필요한 걸 콕 집어 묻고, 운영에 필요한 답만 받으세요.`를 보조 문장으로 사용하되, 모든 화면에 반복하지 않는다.

## SEO · 콘텐츠 담당자

검색 유입 콘텐츠는 키워드 집합이 아니라 해결 절차여야 한다. 예를 들어 ‘교육 신청서’ 글에는 양식 목적, 질문 예시, 개인정보 고지, 마감 설정, 공유·정리의 순서를 담는다. OG 이미지, 제목, 설명, 사이트맵, 내부 링크를 배포 후 확인한다.

**금지:** 실제 사용자 답변·고객명·비공개 운영 데이터를 사례로 쓰지 않는다.

## GRW · 그로스 담당자

분석은 유입→템플릿 열람→폼 생성→첫 질문 추가→공유 링크 생성→7일 재방문 순서만 본다. 답변 원문, 이메일, 개인키, 복구수단을 이벤트에 넣지 않는다. 지표가 낮아도 먼저 인터뷰와 세션 흐름을 보고, 성급하게 UI·가격을 바꾸지 않는다.

## COM · 커뮤니티 담당자

Discord, 카카오, 네이버, 당근, 파트너 채널은 각각 역할이 다르다. 한 채널에 의존하지 않고, 커뮤니티 규칙을 읽은 뒤 실질적인 도움이나 파일럿 제안을 먼저 한다. 홍보성 게시보다 ‘운영자가 실제로 어떤 질문을 받고 무엇이 귀찮은가’를 듣는 것이 목적이다.

## SAL · 컨시어지 운영자

파일럿은 제품을 대신 만들어 주는 서비스가 아니라 사용 장면을 관찰하는 실험이다. 운영자의 실제 질문 구조만 받고 값은 더미로 바꾼다. 세팅 뒤에는 운영자에게 직접 수정·공유·마감·응답 정리를 하게 하고, 막힌 순간만 기록한다.

**종료 질문:** “다음 행사/교육에서 다시 쓸 건가요?”, “안 쓴다면 가장 큰 이유는 무엇인가요?” 두 질문을 반드시 남긴다.

## PEO · 협업 책임자

협업자는 역할별 최소 권한만 받는다. GitHub 쓰기, Supabase 관리자, Cloudflare 배포, 분석 조회 권한을 한 사람에게 기본으로 몰아주지 않는다. 브리프에는 문제, 산출물, 완료 기준, 보지 말아야 할 데이터, 롤백 기준을 포함한다.

## RES · 리서처

경쟁사는 기능 수가 아니라 사용자가 그 제품을 선택하는 상황을 비교한다. 구글폼·네이버폼·예약 도구·스프레드시트·카카오톡을 대체 수단으로 같이 본다. 인사이트는 ‘그래서 무엇을 만들거나 하지 않을지’가 없으면 연구 노트에서 끝난다.

## BCP · 위기 대응 책임자

사고가 나면 먼저 새 배포와 위험한 자동화를 멈춘다. 다음으로 영향 범위, 증거 보존, 사용자 영향, 복구 수단, 공지 시각을 기록한다. 키·암호문·원문을 손대기 전에 백업과 전문가 판단을 우선한다. 사후에는 원인, 탐지 지연, 사용자 영향, 재발 방지 작업을 분리해 기록한다.
