# 핵심 실행 체크리스트

> 아래 다섯 문서는 새 담당자가 가장 먼저 익혀야 하는 실제 실행 순서다. 명령어를 실행하기 전에 항상 현재 저장소 경로와 작업 브랜치, 사용자 영향 여부를 확인한다.

## A. 코드 변경부터 운영 확인까지

### 시작 전

- [ ] 요청을 한 문장으로 요약했다.
- [ ] 이 변경이 새 기능인지, 버그·보안·테스트·접근성 보완인지 구분했다.
- [ ] 새 기능이면 사용자 문제, 대상 사용자, 성공 신호가 기록돼 있다.
- [ ] 작업 트리가 깨끗한지 확인했다.
- [ ] 변경할 파일과 영향을 받는 화면을 적었다.

### 구현·검증

- [ ] 민감정보, 키, 토큰, 실제 응답 원문을 코드·로그·테스트에 넣지 않았다.
- [ ] 오류 경계 밖으로 새 예외가 전파되지 않는지 확인했다.
- [ ] 데스크톱·모바일에서 긴 한국어 문자열과 빈 데이터가 깨지지 않는지 확인했다.
- [ ] `git diff --check`를 실행했다.
- [ ] `npm run build`를 실행했다.

### 배포

- [ ] 커밋 메시지가 변경 목적을 말한다.
- [ ] GitHub Actions의 Cloudflare Pages 작업이 성공했다.
- [ ] 운영 URL에 캐시 무효화 쿼리를 붙여 최신 HTML을 확인했다.
- [ ] 홈, 편집기, 공개 응답 링크 중 영향 화면을 실제로 열었다.
- [ ] 전역 렌더링 오류가 새로 기록되지 않았는지 확인했다.
- [ ] 실패 시 마지막 정상 커밋과 롤백 판단을 기록했다.

### 완료 기록

`날짜 / 커밋 / 변경 목적 / 확인 화면 / 미확인 범위 / 롤백 커밋`을 남긴다.

## B. E2EE 키 백업·복구 안내

### 사용자에게 먼저 말할 것

> 응답 원문을 여는 개인키와 복구 비밀번호는 사용자 기기에만 있습니다. 콕폼은 비밀번호를 알거나 재설정할 수 없습니다. 파일과 비밀번호를 모두 잃으면 암호문은 남아도 열 수 없습니다.

### 최초 폼 생성 직후

- [ ] 개인키 금고를 만든다.
- [ ] 복구 비밀번호가 다른 서비스 비밀번호와 다른지 확인한다.
- [ ] 키 백업 파일 또는 전체 복구 번들을 내려받는다.
- [ ] 파일과 비밀번호를 서로 다른 안전한 곳에 보관한다.
- [ ] 가능하면 다른 기기 또는 오프라인 저장소에서 복구 파일이 존재하는지 확인한다.
- [ ] 실제 응답이 쌓이기 전에 복구 절차를 한 번 연습한다.

### 비밀번호를 잊었을 때

- [ ] 기존 로그인 기기에 열려 있는 금고가 있는지 확인한다.
- [ ] 키 백업 파일 또는 전체 복구 번들이 있는지 확인한다.
- [ ] 복구 파일과 그 파일에 사용한 비밀번호를 사용자 기기에서 직접 입력한다.
- [ ] 고객지원 채널로 키, 파일, 비밀번호, 응답 원문을 보내지 않는다.
- [ ] 모든 복구 수단이 없으면 데이터를 억지로 재설정하지 않는다. 새 키 생성은 기존 암호문을 영구적으로 열 수 없게 만들 수 있다.

### 운영자가 절대 하지 않을 것

- [ ] 사용자의 비밀번호를 직접 받아 입력하지 않는다.
- [ ] ‘비밀번호 초기화하면 응답을 열 수 있다’고 약속하지 않는다.
- [ ] 기존 공개키가 있는 폼에 새 개인키를 임의 생성하지 않는다.

## C. 공개 응답·E2EE 제출 장애

### 5분 안에 확인할 것

- [ ] 공개 링크가 로그인 없이 열리는지 확인한다.
- [ ] 폼이 마감·시작 시간·응답 정원·비밀번호 때문에 닫힌 상태가 아닌지 확인한다.
- [ ] 콘솔 오류를 확인하되 실제 답변·키는 복사하지 않는다.
- [ ] Edge Function 배포 상태와 최근 GitHub Actions 배포 상태를 분리해서 확인한다.
- [ ] 다른 브라우저/네트워크에서 빈 더미 응답으로 재현한다.

### 오류 코드별 안내

| 코드·현상 | 사용자 안내 | 운영 판단 |
|---|---|---|
| `form_unavailable` | “현재 이 양식은 응답을 받지 않아요.” | 마감·기간·공개 설정 확인 |
| `response_limit_reached` | “정원에 도달해 응답을 받을 수 없어요.” | 정원 설정·원자적 제한 확인 |
| `duplicate` | “이 브라우저에서는 이미 제출했어요.” | 브라우저 1회 제한은 신원 보장이 아님 |
| `rate_limited` | “잠시 후 다시 시도해 주세요.” | 대량 제출·오탐 여부 확인 |
| 키 금고 열기 요구 | “작성자 기기에서 복구 수단으로 금고를 열어야 해요.” | 키 불일치·새 키 생성 금지 |

### 사고로 커지는 신호

- 공개 링크 전체가 열리지 않는다.
- 여러 사용자가 같은 시간에 제출 실패를 말한다.
- 응답 암호문이 저장됐지만 작성자가 복호화하지 못한다.
- 키·비밀값 노출 의심이 있다.

이 경우 새 기능 배포를 멈추고 `BCP` 도메인의 사고 감지 매뉴얼로 이동한다.

## D. 컨시어지 파일럿 1회 운영

### 대상 선택

- [ ] 행사, 교육, 커뮤니티 운영자 중 실제로 다음 2주 안에 신청·접수 업무가 있는 사람을 선택한다.
- [ ] 채용, 의료, 금융, 미성년자, 민감정보 수집 폼은 제외한다.
- [ ] Discord만 보지 않고 카카오, 네이버, 당근, 지인 소개, 오프라인 모임 등 최소 2개 채널에서 모집한다.

### 첫 안내

> “실제 신청자 정보는 받지 않습니다. 양식의 질문 구조와 설정만 더미 데이터로 같이 만들고, 응답 내용은 운영자 본인만 보게 진행합니다. 30분 안에 직접 수정·공유·마감까지 해보는 테스트입니다.”

### 세션 진행

- [ ] 최근에 했던 접수 업무를 처음부터 설명하게 한다.
- [ ] 실제 이름·연락처·답변은 더미 값으로 바꾼다.
- [ ] 운영자가 직접 빈 양식 또는 템플릿을 고른다.
- [ ] 운영자가 직접 질문 추가·수정, 고지, 마감, 공유 링크 생성을 수행한다.
- [ ] 막힌 순간, 스스로 해결한 순간, 헷갈린 문구를 시간과 함께 적는다.
- [ ] 응답 원문은 열지 않는다.

### 종료 인터뷰

1. “다음 운영에서도 이걸 다시 쓰겠어요?”
2. “안 쓴다면 가장 큰 이유는 뭐예요?”
3. “대신 쓰던 방법은 무엇이고, 그 방법의 어떤 부분이 더 편해요?”
4. “오늘 직접 하지 못하고 내가 대신한 부분은 뭐예요?”

### 성공 판정

성공은 칭찬이 아니다. 운영자가 실제로 다시 사용하거나, 거절 이유가 명확히 기록됐을 때다.

## E. 개인정보·지원 문의 최소화

### 지원 요청을 받을 때

- [ ] “키/비밀번호/백업 파일/응답 원문은 보내지 마세요”를 먼저 안내한다.
- [ ] 폼 ID, 발생 시각, 브라우저, 오류 문구, 민감정보를 가린 화면만 요청한다.
- [ ] 요청자가 폼 운영자인지 확인한다.
- [ ] 실제 응답자 요청이면 그 폼 운영자에게 문의하도록 안내한다.

### 정책·고지 점검

- [ ] 플랫폼 개인정보처리방침과 각 폼 운영자의 고지를 구분한다.
- [ ] 폼의 수집 목적, 항목, 보관 기간, 문의처가 업무에 맞는지 확인한다.
- [ ] 정보가 해외 서비스로 처리될 가능성이 있으면 관련 안내를 확인한다.
- [ ] 정책을 변경하면 시행일·변경 내용·고지 방법을 기록한다.

### 절대 금지

- [ ] 신청자 원문을 개인 DM·메일·노션·분석 도구로 옮긴다.
- [ ] 답변 원문을 버그 재현 데이터로 복사한다.
- [ ] 법률 검토 없이 ‘완전 준수’ 또는 ‘법적 책임 없음’을 약속한다.
